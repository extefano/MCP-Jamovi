Documento de Requisitos Formales (PRD & SDD)Proyecto: Servidor MCP jamoviMódulo: Infraestructura Fundacional y ContenedorizaciónVersión: 1.2.0 - Arquitectura Resiliente para AgentesMetodología: Spec-Driven Development (SDD) con notación EARS1. Visión y Contexto Arquitectónico (System Context)Este documento define la base para construir un Servidor Model Context Protocol (MCP) destinado a interactuar con el ecosistema analítico de jamovi.Contexto del Dominio:jamovi abstrae la complejidad del lenguaje R detrás de una interfaz gráfica intuitiva y la librería jmv. Para asegurar la reproducibilidad metodológica y mitigar el "infierno de dependencias" en diferentes sistemas, este servidor MCP se construirá nativamente dentro de un contenedor (Docker). Este diseño impone restricciones de aislamiento (headless) que el servidor debe sortear mediante herramientas específicas.Objetivo de esta Fase Inicial:Establecer un servidor MCP robusto y dockerizado que implemente la conexión al entorno R de manera segura, la capacidad de leer la estructura de un dataset mapeado mediante volúmenes utilizando librerías estáticas, y la ejecución del análisis base: Estadísticas Descriptivas (jmv::descriptives()).Stack Tecnológico Definido para el Agente:Contenedorización: Docker (Imagen base sugerida: rocker/r-ver o python:3.10-slim con R base).Protocolo: MCP (Model Context Protocol) operando sobre transporte stdio.Lenguaje del Servidor: Python 3.10+ utilizando el SDK oficial mcp.Puente de Integración R: rpy2 o invocaciones vía subprocess a Rscript.Librerías R Críticas: jmv (para el motor estadístico) y jmvReadWrite (para la lectura segura de archivos .omv en entornos sin interfaz).2. Historias de Usuario (User Stories)US-01 (Portabilidad Docker): Como agente de IA, necesito que el servidor esté empaquetado en Docker para poder desplegarlo e interactuar con él usando flujos de entrada/salida estándar sin preocuparme por las dependencias del host.US-02 (Lectura Segura Headless): Como agente de IA, necesito leer la estructura de un archivo .omv local (mapeado vía volumen) sin depender de servicios web secundarios que puedan fallar en un contenedor aislado.US-03 (Análisis y Serialización): Como agente de IA, necesito ejecutar análisis estadísticos descriptivos con la función jmv::descriptives() y recibir los resultados en un formato JSON estándar, no en un objeto orientado a objetos (R6) propietario de R que no pueda parsear.US-04 (Traducción a GUI): Como usuario humano de jamovi, requiero que la IA me provea la ruta exacta de la interfaz gráfica y los pasos a seguir para replicar manualmente el cálculo realizado por el contenedor.3. Requisitos Formales de Sistema (EARS Syntax)Las siguientes reglas dictan el comportamiento estricto del sistema.3.1. Arquitectura de Contenedor e InicializaciónREQ-01.1 [Ubiquitous]: THE SYSTEM SHALL ejecutarse dentro de un contenedor Docker aprovisionado con R, Python 3.10+, y los paquetes CRAN jmv y jmvReadWrite.REQ-01.2 [Event-driven]: WHEN el cliente MCP (agente) inicialice el servidor vía stdio, THE SYSTEM SHALL validar la presencia de las librerías R requeridas en el entorno.REQ-01.3 [State-driven]: IF las validaciones de entorno fallan, THE SYSTEM SHALL emitir un error fatal controlado al canal stderr y abortar la ejecución.3.2. Herramienta 1: Exploración de Datos (tool_get_dataset_info)REQ-02.1 [Ubiquitous]: THE SYSTEM SHALL exponer la herramienta tool_get_dataset_info que requiera el parámetro dataset_path (string, apuntando a una ruta dentro del volumen del contenedor, ej. /data/...).REQ-02.2 [Event-driven]: WHEN la herramienta sea invocada, THE SYSTEM SHALL utilizar exclusivamente la función read_omv() del paquete jmvReadWrite en R para extraer el marco de datos sin depender de conexiones activas a jamovi.REQ-02.3 [Event-driven]: WHEN se extraiga el marco de datos, THE SYSTEM SHALL retornar un objeto JSON serializado con los nombres de las columnas y sus tipos estadísticos inferidos.3.3. Herramienta 2: Estadísticas Descriptivas (tool_run_descriptives)REQ-03.1 [Ubiquitous]: THE SYSTEM SHALL exponer la herramienta tool_run_descriptives requiriendo los parámetros dataset_path y vars (array de strings).REQ-03.2 [Event-driven]: WHEN se invoque la herramienta, THE SYSTEM SHALL ejecutar la llamada equivalente a jmv::descriptives(data=dataset, vars=vars, ...) en el entorno R subyacente.REQ-03.3 [Event-driven]: WHEN la función devuelva el objeto de resultados de jamovi (instancia de clase R6), THE SYSTEM SHALL forzar la extracción del Data Frame interno invocando la propiedad de tabla correspondiente (ej. resultado$descriptives$asDF) antes de intentar la serialización a JSON.REQ-03.4 [Ubiquitous]: THE SYSTEM SHALL incluir en el objeto JSON de respuesta un nodo gui_instructions inmutable con el valor: "Para replicar esto en jamovi: Vaya a 'Exploration' -> 'Descriptives' y arrastre las variables {vars} al cuadro 'Variables'."4. Restricciones Técnicas y Estándares de Codificación (Critical Fixes)CON-01 (Aislamiento de Código): Prohibido el uso de la evaluación de strings de código R crudo inyectado por el LLM (eval(parse(text=...))). Todas las llamadas a R se realizarán mediantes wrappers estructurados o subprocesos parametrizados para prevenir inyecciones de código.CON-02 (Inmutabilidad del Dataset): El contenedor tratará el volumen de datos montado (/data) como de solo lectura.CON-03 (Validación de Esquema Pydantic): El servidor implementará pydantic para validar estructuralmente los argumentos JSON de las herramientas MCP.CON-04 (Parche R6-a-JSON): El servidor MCP en Python debe tener rutinas específicas para manejar la transformación de objetos R6 de la librería jmv. Intentar usar jsonlite::toJSON directamente sobre el objeto retornado por las funciones de jmv provocará un volcado de memoria o un error de conversión R6. Siempre se debe acceder a las propiedades $asDF de las tablas resultantes.CON-05 (Heurística de Rutas de Volumen): Dado que el servidor se ejecuta dentro de un entorno Docker, el LLM debe ser instruido por este documento a no enviar rutas absolutas del host de usuario (como C:\Users\...). El LLM deberá construir la ruta asumiendo un punto de montaje estándar definido en la ejecución del servidor (por ejemplo, prependiendo /data/ al nombre del archivo), y el código del servidor validará la existencia del archivo en dicha ruta interna.
