Documento de síntesis operativa y plan de ejecución
Proyecto: Servidor MCP jamovi
Estado: base documental consolidada

1. Objetivo
Construir un servidor MCP local y dockerizado para jamovi, con un puente seguro a R y una capa de traducción que convierta resultados estadísticos en instrucciones reproducibles para la GUI de jamovi.

2. Decisiones confirmadas por las especificaciones
- El servidor se implementará en Python 3.10+.
- La ejecución del MCP arrancará por stdio en la primera fase.
- El entorno estará encapsulado en Docker.
- La lectura de datos se hará con jmvReadWrite y read_omv() para archivos .omv.
- Los análisis estadísticos se resolverán en R mediante jmv.
- La serialización hacia el cliente será JSON estructurado.
- La conversión de resultados R6 a salida usable deberá extraer tablas con asDF antes de serializar.
- La validación de argumentos se realizará con Pydantic.
- No se permitirá eval(parse(text=...)) ni evaluación de código R inyectado.
- El volumen de datos montado se tratará como de solo lectura.

3. Alcance funcional de la primera iteración
3.1 Herramientas iniciales
- tool_get_dataset_info
- tool_run_descriptives

3.2 Salida esperada
- Metadatos del dataset: nombres de columnas y tipos inferidos.
- Resultados descriptivos: tablas serializadas a JSON.
- Instrucciones GUI inmutables para replicar el análisis en jamovi.

4. Riesgos técnicos ya identificados
- Incompatibilidad entre objetos R6 y serialización directa a JSON.
- Dependencias de R no presentes en el contenedor.
- Divergencia entre rutas del host y rutas internas del contenedor.
- Ambigüedad entre transportes stdio y SSE en los documentos de diseño; para la base se prioriza stdio.

5. Criterios de aceptación mínimos
- El servidor inicia en Docker sin depender del host para ejecutar R.
- La herramienta de exploración devuelve estructura del dataset sin exponer el archivo completo.
- La herramienta de descriptivos ejecuta jmv::descriptives y retorna resultados parseables.
- La respuesta incluye instrucciones GUI reproducibles.
- La validación rechaza parámetros inválidos antes de llegar a R.

6. Plan de ejecución por fases
Fase 1: Fundaciones del repositorio
- Definir estructura de proyecto.
- Alinear README, documentación técnica y supuestos de arranque.
- Preparar Dockerfile base y dependencias.

Fase 2: Núcleo MCP
- Implementar servidor MCP en Python.
- Registrar herramientas y esquema de validación.
- Añadir manejo de errores controlado.

Fase 3: Puente a R
- Conectar lectura de datos con jmvReadWrite.
- Crear capa segura de invocación a jmv.
- Resolver extracción de tablas R6 mediante asDF.

Fase 4: Traducción GUI
- Mapear análisis a rutas de menú de jamovi.
- Generar instrucciones de reproducción manual.
- Incluir parámetros visibles en el texto final.

Fase 5: Robustez
- Añadir pruebas básicas.
- Verificar límites de entrada.
- Revisar memoria, errores de R y comportamiento del contenedor.

7. Próximo paso inmediato
- Crear el esqueleto del servidor MCP y el Dockerfile base, con validación de entorno y una primera implementación de tool_get_dataset_info.

Informe Técnico: Arquitectura y Especificaciones para un Servidor MCP Basado en jamovi e Inteligencia Artificial AgénticaIntroducción y Análisis de Entorno ParadigmáticoEl ecosistema de análisis de datos y la investigación cuantitativa han experimentado una transformación fundamental con la convergencia de interfaces gráficas accesibles y lenguajes de programación estadística sumamente robustos. Históricamente, la brecha metodológica entre el estadístico computacional y el investigador aplicado presentaba un obstáculo significativo. En este contexto, el software estadístico jamovi se ha consolidado como una plataforma primordial y disruptiva, proporcionando un entorno interactivo de hoja de cálculo que opera subrepticiamente sobre el motor estadístico del lenguaje R. Al abstraer la inmensa complejidad algorítmica y sintáctica del código R detrás de una interfaz de usuario altamente intuitiva e interactiva, estructurada mediante archivos de definición de diseño como los .a.yaml y .u.yaml , jamovi reduce drásticamente la barrera de entrada al análisis estadístico riguroso y mejora sustancialmente la curva de aprendizaje frente a sistemas tradicionales como SPSS.Sin embargo, el advenimiento y la proliferación de modelos de lenguaje grande (LLMs) y arquitecturas agénticas introducen la inminente necesidad de flujos de trabajo automatizados impulsados por Inteligencia Artificial (IA). Este paradigma emergente requiere un nuevo nivel de interacción técnica: la capacidad de que agentes autónomos interactúen de manera programática con el motor subyacente de jamovi, procesen conjuntos de datos, ejecuten razonamiento estadístico iterativo y, de manera crítica, traduzcan sus operaciones subyacentes en instrucciones perfectamente comprensibles para usuarios humanos que carecen de conocimientos técnicos avanzados. El Model Context Protocol (MCP), un estándar arquitectónico universal de código abierto introducido para conectar agentes de IA con fuentes de datos y herramientas externas , emerge como la topología de red óptima para resolver este desafío de integración.La implementación de un servidor MCP diseñado específicamente para orquestar la interfaz de programación de aplicaciones (API) interna de jamovi y su paquete homólogo jmv en R, habilita una capa de interoperabilidad universal sin precedentes. Esta arquitectura permite que aplicaciones cliente de LLMs actúen como agentes analíticos altamente especializados, orquestando pruebas estadísticas complejas a partir de interacciones conversacionales en lenguaje natural, al tiempo que preservan la trazabilidad científica y la reproducibilidad algorítmica mediante la generación de directrices procedimentales para la interfaz gráfica del usuario (GUI).Evaluación de Topologías de Despliegue: Infraestructura en la Nube frente a Ejecución LocalEl diseño axiomático de una arquitectura dirigida a usuarios sin conocimientos técnicos exige una evaluación rigurosa y exhaustiva del modelo de despliegue del servidor MCP. Históricamente, el uso de herramientas de interoperabilidad integradas con agentes de IA en entornos locales ha requerido que los usuarios configuren de manera manual entornos de desarrollo, gestionen intérpretes de Python, instalen múltiples dependencias de lenguajes compilados como R o C++, manipulen registros del sistema y administren variables de entorno complejas. Para el usuario demográfico principal de jamovi, que busca evitar la fricción de la línea de comandos , esta carga operativa representa una fricción de adopción inaceptable. El siguiente análisis desglosa las viabilidades operativas del despliegue local frente a las soluciones basadas en plataformas en la nube de nivel gratuito.El despliegue local de un servidor MCP diseñado para acoplarse a jamovi implica orquestar de manera síncrona una multitud de procesos anidados que son altamente dependientes del sistema operativo anfitrión. La arquitectura de la aplicación de escritorio de jamovi depende intrínsecamente de una jerarquía de ejecución sumamente delicada. Durante la secuencia de inicio, un proceso base de la interfaz Electron (jamovi.exe) inicia el servidor asíncrono subyacente programado en Python (basado en el marco de trabajo web Tornado), el cual a su vez lanza procesos paralelos del motor desarrollados en C++ (jamovi-engine.exe) encargados de inicializar e interactuar con el entorno integrado de R. En los sistemas operativos corporativos o académicos, particularmente bajo distribuciones de Windows, las restricciones impuestas por las políticas administrativas y los firewalls frecuentemente bloquean de forma arbitraria la ejecución de binarios no firmados, o interceptan las comunicaciones de sockets entre los ejecutables python.exe y jamovi-engine.exe. Cuando se presentan fallos en esta cadena de inicio, el diagnóstico requiere herramientas de análisis de eventos profundos como el Process Monitor de Microsoft, una tarea que excede ampliamente el alcance cognitivo y técnico de un investigador de ciencias sociales promedio.Más allá de la complejidad del inicio del sistema, la integración de un cliente MCP local introduce vectores de error adicionales. Si bien jamovi soporta integraciones analíticas externas mediante la instalación del paquete jmv o la comunicación de datos a través de los paquetes jmvReadWrite y jmvconnect en una sesión interactiva de R , requerir que un usuario final no técnico instale dependencias como Node.js o Python, configure herramientas como npm o pip para obtener los SDKs correspondientes, orqueste la comunicación de datos interprocesos mediante JSON-RPC sobre canales de entrada y salida estándar (stdio), e inicialice un inspector MCP desde la consola de comandos, resulta absolutamente inviable. El paradigma de infraestructura como código y las dependencias de red introducen un riesgo inminente de fallos de configuración que frustrarían la adopción de la herramienta.Como contraparte arquitectónica, el despliegue del servidor MCP en plataformas en la nube con niveles de servicio gratuitos, como Hugging Face Spaces o Render, ofrece un modelo de infraestructura inmutable, reproducible y preconfigurada que elimina de raíz los obstáculos inherentes a las instalaciones locales. La tecnología de contenedores, específicamente la implementación de Docker, permite empaquetar el ecosistema completo en un entorno virtual aislado y autónomo. En Hugging Face Spaces, por ejemplo, los ingenieros pueden definir un archivo Dockerfile maestro que encapsule una instalación limpia de una distribución de Linux, la versión exacta del lenguaje R requerida (asegurando versiones superiores a la 4.3 para soporte nativo de caracteres Unicode ), las bibliotecas matemáticas del sistema operativo, el paquete jmv directamente desde el repositorio CRAN , la interfaz de enlace rpy2 para la comunicación entre Python y R , y finalmente el servidor de protocolo MCP desarrollado en Python.La principal y decisiva ventaja de este enfoque de virtualización en la nube radica en la abstracción integral de la complejidad de la infraestructura de cara al usuario final. En este modelo, el usuario interactúa única y exclusivamente con su entorno cliente de IA conversacional predilecto, como una aplicación web nativa, un cliente de Claude Desktop o una integración de chat. El cliente actúa como un conducto que se conecta de forma totalmente transparente al servidor MCP remoto alojado en la nube. Esta comunicación no utiliza los flujos locales de stdio, sino que aprovecha los protocolos estándar de internet, exponiendo los puntos finales de las herramientas de IA mediante HTTP utilizando flujos de eventos enviados por el servidor (Server-Sent Events o SSE) o un proxy web estandarizado. Esta separación de preocupaciones asegura que la versión en la nube aísla el entorno de análisis de cualquier anomalía originada en el estado del sistema operativo local del usuario, haciéndolo virtualmente inmune a las configuraciones locales defectuosas o a las políticas restrictivas de los departamentos de tecnologías de la información institucionales.Dimensión de Análisis ComparativoArquitectura de Despliegue LocalInfraestructura en la Nube (Docker en Hugging Face Spaces)Fricción de Instalación y AdopciónExtremadamente alta; Si bien la teoría indica que la ejecución de motores estadísticos locales garantiza una privacidad de datos hermética si el equipo se desconecta completamente de internet , las implementaciones modernas de contenedores altamente seguros, cifrado en tránsito, aislamiento de inquilinos y políticas de terminación de sesiones efímeras en la nube mitigan sustancialmente estos riesgos de seguridad perimetral sin comprometer un ápice de usabilidad.Arquitectura Profunda: Integración del Protocolo MCP, JSON-RPC y el Motor de jamoviEl desarrollo de este sistema unificado requiere una disección profunda de la intersección teórica y técnica entre el protocolo de contexto de modelos (MCP) y el motor estadístico subyacente estructurado en R. El protocolo MCP opera conceptualmente sobre una intrincada arquitectura cliente-servidor distribuida. En este paradigma, un Host (usualmente la aplicación interactiva que aloja el modelo de lenguaje de IA) coordina de forma orquestada con múltiples Servidores MCP. Estos servidores actúan como proveedores de capacidades especializadas, exponiendo recursos de datos persistentes, plantillas de indicaciones (prompts) enriquecidas y, crucialmente, herramientas (tools) con tipado paramétrico fuerte que el agente puede invocar de forma autónoma para alterar su entorno o ejecutar cálculos.El flujo de información subyacente de esta arquitectura se rige de manera absoluta por el estándar JSON-RPC 2.0. JSON-RPC es un protocolo de llamada a procedimientos remotos (RPC) sumamente ligero y apátrida (stateless) que utiliza el formato de intercambio de datos JSON para codificar y decodificar los mensajes. Su diseño permite el envío bidireccional, síncrono y asíncrono de estructuras de datos arbitrariamente complejas, siendo independiente del protocolo de transporte subyacente (operando transparentemente sobre HTTP, WebSockets o flujos estándar). Dentro de la estructura JSON-RPC, el servidor de jamovi MCP procesará solicitudes que contienen un método específico ordenado por la IA (por ejemplo, ejecutar un análisis estadístico) e inyectará los resultados procesados dentro del bloque de respuesta formateado según las estrictas convenciones del estándar, evitando ambigüedades en la interpretación de los datos estadísticos resultantes.Gestión Avanzada de Estado y Persistencia Estructurada de SesionesUna característica absolutamente crítica en la viabilidad técnica de los flujos de trabajo de análisis de datos impulsados por agentes multimodales es el manejo persistente del estado. El comportamiento algorítmico estándar de los Modelos de Lenguaje Grandes (LLMs) y de las primeras implementaciones de los servidores MCP es intrínsecamente apátrida (stateless). Esto significa que, por defecto, ni el modelo ni el servidor retienen el contexto acumulativo o el historial de mutaciones de datos entre diferentes llamadas a herramientas consecutivas. En el contexto riguroso del análisis de conjuntos de datos empíricos con herramientas como jamovi, intentar enviar el bloque de datos completo (que podría constar de millones de celdas) de ida y vuelta a través de la red y reinsertarlo en la ventana de contexto del LLM en cada operación estadística independiente resulta algorítmicamente prohibitivo. Este enfoque ingenuo agotaría casi inmediatamente los límites máximos de tokens del modelo de lenguaje, multiplicaría de forma insostenible los costos de inferencia de la API y degradaría severamente la latencia del sistema hasta volverlo inoperable.Para solucionar este impedimento arquitectónico fundamental, el servidor MCP debe trascender el diseño básico e implementar un paradigma orquestado conocido como Context-Aware MCP (CA-MCP). Esto implica una desviación del comportamiento apátrida puro; el servidor debe asumir la completa responsabilidad de alojar y mantener el conjunto de datos activo. Esta mantención se realiza cargando el archivo de datos en memoria (representado como un objeto data.frame o un tibble activo dentro de una sesión persistente del entorno de R subyacente, gestionado a través de la librería puente rpy2 en Python o mediante llamadas asíncronas directas al motor binario en C++). Para identificar inequívocamente a quién pertenece este estado en memoria, el CA-MCP gestiona un Almacén de Contexto Compartido (Shared Context Store) utilizando un Identificador de Sesión único y criptográficamente seguro (session_id).En esta topología avanzada, las herramientas agénticas de la IA nunca manejan la carga útil de los datos en sí. Simplemente, pasan metadatos como referencias de nombres de columnas, operadores lógicos y parámetros estadísticos discretos al servidor junto con el token de sesión. El servidor CA-MCP recupera el entorno de R correcto correspondiente a ese token, ejecuta el cálculo complejo de álgebra matricial sobre el estado masivo retenido en memoria, y devuelve exclusivamente una representación comprimida, estructurada y semánticamente rica (típicamente en formato JSON) y un resumen en texto claro del resultado estadístico.La implementación obligatoria de persistencia de sesiones requiere precauciones exhaustivas en materia de seguridad informática y gestión de memoria. El servidor no solo debe generar los tokens de estado seguros, sino que está obligado a implementar heurísticas estrictas de inactividad (timeouts). Un recolector de basura (garbage collector) de nivel de aplicación debe monitorear el acceso a cada bloque de memoria. Si una sesión se abandona, el sistema debe purgar activamente de la memoria del servidor en la nube todos los conjuntos de datos asociados para liberar recursos. Adicionalmente, se debe implementar un control de acceso basado en roles o aislamientos rígidos para asegurar de manera garantizada que cada espacio de trabajo está herméticamente sellado, previniendo así cualquier fuga de datos o contaminación cruzada entre múltiples investigadores que consulten la infraestructura de nube simultáneamente en escenarios de multitenencia (multitenancy).Integración Algorítmica con el Motor Central de jamovi (jmv)El núcleo estadístico e inferencial de toda la suite de jamovi opera mediante la exposición de sus capacidades a través del paquete nativo de R denominado jmv. Este paquete engloba, empaqueta y estandariza todas las funciones analíticas que se encuentran mapeadas visualmente en la interfaz interactiva del usuario. La arquitectura del servidor MCP concebida actuará esencialmente como una envoltura de middleware inteligente (wrapper) programada en Python. Su función es recibir las instrucciones codificadas en JSON-RPC enviadas asíncronamente por el LLM, validarlas rigurosamente contra un esquema estático estricto (utilizando librerías de serialización como pydantic o esquemas anidados integrados directamente en el SDK de tipado estricto de MCP), y finalmente, utilizar esta validación para construir la llamada sintáctica exacta en lenguaje R.La invocación real al ecosistema subyacente de R se ejecuta importando el paquete jmv dentro de la sesión de rpy2 y mapeando los diccionarios de Python a los argumentos funcionales de R. A modo ilustrativo, una llamada hipotética generada por la IA para calcular matrices de correlación bivariadas, incluyendo niveles de significancia y factores atenuantes, se transforma programáticamente en el puente R como la función: jmv::corrMatrix(data = espacio_de_trabajo_activo, vars = vars(Var1, Var2), pearson = TRUE, sig = TRUE, flag = TRUE). El resultado computado de estas complejas operaciones en R no retorna meramente una matriz numérica, sino que devuelve un objeto de clase enriquecido (Object containing active bindings). Este objeto posee la capacidad intrínseca de autodescribirse y, al ser evaluado o impreso mediante funciones de renderizado, genera tablas preformateadas de alta calidad en formato ASCII y texto formateado explicativo. Este texto resulta ideal para ser embebido y devuelto de manera eficiente al LLM como parte fundamental del objeto de respuesta tipificado como structuredContent, cumpliendo íntegramente con las estipulaciones de diseño de respuestas del protocolo MCP.Diseño de la Inteligencia Agéntica: Definición Semántica de Herramientas (Tools)Para que el modelo de lenguaje avanzado pueda operar de manera verdaderamente autónoma e inferir intenciones de análisis implícitas en las consultas del usuario, el servidor MCP debe exponer un catálogo predefinido de herramientas estadísticas sumamente precisas y acotadas. En el glosario del protocolo MCP, estas herramientas actúan funcionalmente como rutinas con tipado declarativo fuerte que el LLM descubre y puede invocar libremente. El diseño de estas interfaces de herramientas no debe ser arbitrario; debe emular fidedignamente la estructura jerárquica y los metadatos de los archivos de configuración .a.yaml (Analysis Definition) originales de la base de código de jamovi.
